## System Role (Phase 1 + 3)

PDE is a **recommendation engine**, not an authority.

```
DGIC (Pritesh Patra)
      ↓  dgic_reasoning
    PDE  ← this system
      ↓  policy_decision
   RAJYA (Rajaryan Verma)  ← final authority
      ↓
  Sarathi (Hemanth)        ← enforcement
      ↓
   Core (Raj Prajapati)    ← execution
```

PDE does NOT:
- validate execution_id globally
- enforce or block execution
- act as final authority

PDE ONLY:
- validates DGIC input structure and hash
- applies policy conditions
- returns a structured recommendation

## Phase Breakdown

### Phase 1 — Rename & Reposition
- `sarathi_engine.py` → `pde_engine.py`
- `decision_contract.py` → `pde_contract.py`
- `test_sarathi.py` → `test_pde.py`
- `main.py` rewritten — no enforcement imports
- `enforcement.py` left in place (belongs to Sarathi/Hemanth, not touched)

### Phase 2 — PDE Input Contract
New `dgic_reasoning` shape (replaces flat `dgic_output`):
```json
{
  "execution_id": "...",
  "dgic_reasoning": {
    "decision": "...",
    "confidence": 0.0,
    "epistemic_state": "...",
    "reason_trace": [],
    "execution_hash": "sha256hex",
    "collapse_trigger": false
  }
}
```
Hash computation: `SHA256({execution_id, dgic_reasoning_without_execution_hash})`

### Phase 3 — Authority Behavior Removed
- `enforcement.py` not imported anywhere in PDE
- `pde_engine.evaluate()` returns recommendation dict, never blocks
- No `authorized` field, no gate logic

### Phase 4 — Policy Engine Retained
- `_match_condition()` dispatch table preserved
- `evaluate()` loops `deny_conditions` → `escalation_conditions` → `allow_conditions`
- Zero inline conditions

### Phase 5 — RAJYA-Compatible Output
```json
{
  "execution_id": "...",
  "policy_decision": {
    "decision": "ALLOW | DENY | ESCALATE",
    "reason": "...",
    "confidence": 0.0,
    "policy_version": "...",
    "timestamp": "ISO8601",
    "decision_hash": "sha256hex"
  }
}
```
RAJYA can verify `decision_hash` = SHA256(`{execution_id, decision, reason, policy_version}`) without re-running PDE.

### Phase 6 — Contract Hardening
- Strict key match (`actual == required`) on both payload and `dgic_reasoning`
- Hash bound to `execution_id + dgic_reasoning`
- Extra keys → `invalid_schema` → DENY recommendation (Case 7 proves this)
