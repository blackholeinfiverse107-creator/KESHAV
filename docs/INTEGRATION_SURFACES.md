# Ecosystem Participation Integration Surfaces

This document outlines the attachment surfaces for integrating the KESHAV validation and trust layer into the broader BHIV ecosystem. It maps out dependencies, boundaries, and failure domains to ensure deterministic execution and verifiable provenance without relying on local-only assumptions.

## 1. Upstream Systems
The systems that provide input, telemetry, or requests to the trust layer.
*   **KESHAV:** Provides raw telemetry, task execution graphs, and snapshot data.
*   **InsightFlow:** Provides high-level execution context and pipeline tracking.
*   **Pravah:** Streams state transitions and event data.
*   **NICAI:** Submits structured policy constraints and governance boundaries.

## 2. Downstream Systems
The systems that consume outputs and proofs generated by the trust layer.
*   **BHIV Core Runtime:** Consumes execution validation and trust verification results to determine if runtime progression is allowed.
*   **Replay Ledger (Persistent):** Distributed log that stores consensus proofs, replay validation matches, and trust artifacts.

## 3. Authority Owned Boundaries
These are the domain boundaries that the KESHAV integration layer strictly governs and executes deterministically.
*   **Replay Verification:** Deterministically verifying past execution states against canonical replays.
*   **Execution Validation:** Continuous invariant checking and drift detection on incoming execution traces.
*   **Consensus Verification:** Guaranteeing identical outputs across repeated execution validation cycles.
*   **Trust Verification:** Final issuance of proof confidence metrics to the BHIV Core Runtime.

## 4. Authority Not Owned
Boundaries where the system relies on external constraints and must fail safely if the external system misbehaves.
*   **Raw Telemetry Generation:** Relies on upstream systems to send structured telemetry (though it validates the structure).
*   **Business Logic Execution:** Does not execute or validate the core business logic of KESHAV/InsightFlow, only the *provenance* and *determinism* of that execution.
*   **Ledger Persistence Availability:** Relies on the external distributed ledger to persist proofs; if unavailable, the system buffers or fails securely.

## 5. Runtime Dependencies
To operate in a production distributed environment, the system mandates:
*   **Distributed State Store:** No reliance on local disk for snapshots. All execution boundaries utilize distributed object stores (e.g., S3-compatible or BHIV distributed storage).
*   **Clock Synchronization:** Distributed tracing relies on synchronized logical or physical clocks for cross-layer consistency.
*   **Network Addressing:** Discovery services must dynamically locate the Health and Capability APIs.

## 6. Failure Boundaries
*   **Validation Failure (Deterministic):** If validation fails, a structured violation is returned to the BHIV Core Runtime. Execution halts deterministically.
*   **Upstream Disconnect:** If Pravah/InsightFlow disconnects, the validation engine enters a holding state (Warm Restart mode) until connectivity is restored.
*   **Consensus Drift:** If repeated snapshotting yields different hashes, the system asserts a `NON_DETERMINISTIC` fault and halts trust verification.

---
*Note: All "local-only" assumptions (like writing direct files to `/tmp` or relying on local memory without state replication) have been identified and formally designated to use the BHIV Core Runtime's state distribution interfaces.*
